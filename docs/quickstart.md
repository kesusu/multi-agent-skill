# Multi-Agent Skill 5 分钟快速上手

## 前置条件

- Claude Code（需要 Claude 订阅）
- 无代码、无依赖，一个 `.md` 文件即装即用

## 安装

```bash
git clone https://github.com/kesusu/multi-agent-skill.git
cp multi-agent-skill/commands/multi-agent.md ~/.claude/commands/multi-agent.md
```

重启 Claude Code，输入 `/multi-agent` 验证命令已注册。

## 第一个任务

```bash
/multi-agent Python 的 *args 和 **kwargs 有什么区别？
```

分流器自动判定：`Q1=一个答案` / `Q2=简单` / `Q3=代价不大` → **极简模式**。不派 Agent，不写复盘，直接回答。和不用 skill 没区别，这才是对的——简单任务不应该走流程。

## 核心对比：同一个复杂任务，两种做法

以下数据来自真实 A/B 实验（Task C）。

**任务**：设计多人协作文档冲突方案（10人编辑、离线5-30分钟、版本历史+回滚、自动合并）

### 不用 skill

Claude Code 直接给完整方案：
- 数据模型（Document→Branch→Version→Operation）
- OT+CRDT 三层合并
- 列出 6 个潜在问题
- **1 轮交付，看起来没问题**

问题：方案自洽，但没人质疑设计选择本身。比如选了 Lamport 时钟做因果序——合不合理？不知道，因为没有第二双眼睛看过。

### 用 skill

```
/multi-agent 设计多人协作文档冲突解决方案...
```

执行过程：
1. **分流器** → 判框架模式（要方案、跨领域、有约束）
2. **第1批并行**：架构师（数据模型+合并策略）+ 存储工程师（持久化方案）+ 场景压力测试员（极端场景推演）
3. **第2批**：批评家审查全部产出
4. 批评家找到 **2 个严重漏洞**：
   - **Lamport 时钟因果链断裂**：网络分区重连后，分区内的逻辑时钟无法对齐，因果序不可靠 → 改为 HLC（混合逻辑时钟）
   - **客户端缓存缺失**：方案只服务端存储，离线客户端无本地缓存 → 每次操作都要全量网络请求
5. 修正后交付 v2.0

### 关键差异

| | 不用 skill | 用 skill |
|---|---|---|
| 交付轮数 | 1 轮 | 2 轮 |
| 批评家 | 无（自己审查自己） | 有（强制对抗审查） |
| 发现的设计漏洞 | 0 个 | 2 个严重漏洞 |
| Lamport 时钟问题 | 没被质疑 | 被挑战→改用 HLC |

**核心结论**：多 Agent 的价值不在"产出更多"，在"找到自己漏掉的问题"。

### 这对你意味着什么

不用 skill 的方案**不是烂方案**——它自洽、覆盖了全部 4 个约束。问题在于：**单 Agent 不会质疑自己的设计选择**。选 Lamport 时钟时给了理由，但没人挑战这个理由对不对。

批评家干的事不是"找错别字"，是**质疑你做了但没验证的假设**。上线后发现因果链断裂的修复成本，远不止多花的那一轮时间。

> 诚实提醒：这是 1 个任务的数据（样本量 1）。它证明了"批评家能发现问题"是可能的，不能证明"每次都一定能"。

## 分流器速览

任务到达时，分流器问 3 个问题决定走哪条路：

| 问题 | 判据 |
|---|---|
| Q1: 要"一个答案"还是"一套方案"？ | 答案 → 倾向极简 |
| Q2: 简单吗？ | 单文件/明确改动点/无外部依赖 → 是 |
| Q3: 搞错了代价大不大？ | 钱/安全/公开发布 → 不大 |

| 模式 | 触发条件 | 行为 |
|---|---|---|
| 极简模式 | Q1=答案 ∧ Q2=是 ∧ Q3=不大 | 直接回答，不派 Agent |
| 框架模式 | Q1=方案 ∧ 需求清晰 | 拆解→并行→验收，跳过探针 |
| 探针+框架 | 其余 | 先用探针挖掘需求，再走框架 |

## 核心机制（一句话）

- **并行分工**：多个 Agent 同时处理独立子任务，调度员中转，Agent 间不直接对话
- **对抗审查**：批评家必须存在；找不到问题则引入第二批评家，强制挑战每个设计决策
- **验收闭环**：每轮逐项检查需求匹配度，不是最后才验一次
- **经验沉淀**：复盘经验写入 memory，下次遇到类似任务自动加载历史教训
