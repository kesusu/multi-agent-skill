## 2. 核心模块（别动）

以下5个机制改了框架就会失效，对应failure_cases.md中v1膨胀（失败1）和并行依赖错误（失败3）的教训：

| 机制 | 位置 | 为什么不能动 |
|---|---|---|
| 分流器前置判断 | 14-28行 | 没有分流=所有任务走完整流程=v1膨胀（334行的教训） |
| 执行者≠批评家 | 416行"强制对抗" | 自己审查自己=质量保证归零，这是整个框架的核心价值 |
| 审计员独立于调度员 | 168-215行 | 调度员控制审计=自我声明，等于没有审计 |
| 产出验证（Read确认） | 142-149行 | Agent声称改了≠实际改了（doc-pipeline踩坑：声称修改6个函数，文件中未变） |
| 问题修复计数器 | 476-477行 | 同一问题修3次以上必须停，防止无限循环打补丁 |

**红线**：不要试图把502行精简到200行同时保留以上5个机制。v4砍了40%内容，但保留了这些核心。你可以精简其他部分。

## 3. 定制区（放心改）

### 定制区A：分流器问题（18-20行）

3个问题决定了你的分流逻辑。当前设计是通用的，你可以替换为领域特定的判断：

```
当前：Q1: 要"一个答案"还是"一套方案"？
      Q2: 这件事是否简单？（单文件/明确改动点/无外部依赖）
      Q3: 搞错了代价大不大？（钱/安全/公开发布）

示例（运维团队）：
      Q1: 这次变更是否影响生产环境？
      Q2: 是否有经过验证的回滚方案？
      Q3: 是否需要数据库迁移？
```

只改问题文本和对应的模式判断表（22-26行），保留"3个yes/no→分流"的结构。

### 定制区B：角色配置表（396-403行）

4行示例表可以扩展为你团队常用的角色组合：

```
当前：
| 理论探讨 | 理论家 + 研究员 + 批评家 + 验收者 |
| 工程实现 | 架构师 + 执行者 + 代码审查员 + 测试员 |

示例（加一行）：
| 数据管道 | 管道架构师 + ETL执行者 + 数据质量审查员 |
```

### 定制区C：质量红线阈值（468-478行）

触发条件可以调整阈值：

- 第1条"连续两轮给相同批评"：如果你的场景容易反复修改，可以改为3轮
- 第6条"连续两轮修补没突破"：同上，可改为3轮
- 第7条"达到3次"：高频迭代场景可改为4次

可以删除不适用于你场景的红线（如第8条"用户暂停信号"在自动化场景中不适用）。

### 定制区D：反模式清单（481-502行）

19条中可以删减不适用的、添加你场景特有的反模式。例如：

```
可删：第16条（极简模式下自检审计不适用你的场景）
可加：#20. 跳过数据验证直接修改生产配置
```

### 定制区E：复盘纪要模板（272-298行）

格式可以精简。例如去掉"版本演进"节（简单任务不需要），或加入你团队关心的维度（如"代码覆盖率变化"）。

## 4. 入门修改：3个5分钟能改的点

### 修改1：改分流器问题（改18-20行+22-26行的判断表）

**改前**：
```
1. Q1：用户要的是"一个答案"还是"一套方案"？
2. Q2：这件事是否简单？
3. Q3：搞错了代价大不大？
```

**改后**（数据分析团队）：
```
1. Q1：需要跑生产数据还是只看文档就行？
2. Q2：数据量是否超过100万行？
3. Q3：结果是否会影响业务决策？
```

判断表相应调整：Q1=文档 ∧ Q2=小数据 ∧ Q3=不影响 → 极简模式。

### 修改2：加一行角色配置（改396-403行的表）

**改前**：4行示例

**改后**（加1行）：
```
| 代码重构 | 架构师 + 执行者 + 代码审查员 + 回归测试员 |
```

这是最安全的修改——只加不改，不影响已有逻辑。

### 修改3：删2条不适用的反模式（改481-502行）

如果你的使用场景不需要探针Agent（比如你只处理工程任务），可以删掉反模式第1条中关于探针的部分，以及第9条中不相关的描述。每删一条，行数减少，阅读负担降低。

## 5. 怎么验证你的改动

### 快速验证（改完后立刻做）

1. **分流器测试**：构造3个任务——一个明确极简、一个明确复杂、一个边界case。用改后的分流器判断，看分流结果是否符合你的预期。
2. **角色测试**：用你新加的角色配置跑一个真实任务，看批评家是否给出了不同视角（而非和执行者说一样的话 = 假分工）。
3. **红线测试**：故意让同一个bug出现3次（或你改后的阈值），看是否触发暂停。

### 深度验证（用真实任务跑1-2周）

- **审计是否生效**：看审计报告的8项检查中，pass/fail判定是否基于真实证据而非套话
- **经验是否沉淀**：跑3个任务后检查memory文件，看经验是否被读取并转化为检查点
- **假分工检测**：不同Agent的结论是否有实质性分歧？如果没有，说明角色拆分无效

### 失败判断

| 现象 | 说明 | 怎么修 |
|---|---|---|
| 所有任务都走完整流程 | 分流器判断条件太宽松，没人触发极简模式 | 放宽Q2的"简单"标准 |
| 批评家总说"看起来不错" | 角色prompt太模糊 | 给批评家加具体的检查清单 |
| 审计全是pass | 审计条件太松，或审计员prompt没强调"看证据" | 检查审计员prompt是否包含"忽略调度员自检声明" |
| 同一问题修了5次没人停 | 计数器机制没被正确触发 | 检查计数器是否由非执行者维护 |

**核心原则**：先改一个点，跑3个任务验证，再改下一个。不要一次改完再验证——改坏了你不知道是哪个改的。
