# 失败案例：方法论踩过的坑

以下是从 11 个版本迭代中提炼的失败经历。每个案例包含：发生了什么、为什么错、怎么改的。

---

## 失败 1：v1 过度膨胀（最严重的架构失败）

**发生了什么**：第一版试图把所有能想到的机制都塞进去——固定角色池、写死的流程步骤、堆叠的规则。写完 334 行，发现角色之间职责重叠（"批评家"和"代码审查员"到底谁负责找问题？），流程步骤自相矛盾（某个步骤要求并行，另一个步骤要求串行但没说明跟谁）。

**为什么错**：犯了"加法思维"的错误——每想到一个好规则就加进去，没有检查新规则跟已有规则是否兼容。更深层的原因是没有"分流"概念：所有任务都走同一条完整流程，导致流程必须兼容所有情况，自然越来越复杂。

**怎么改的**：v4 大规模精简（334→208行），砍掉近 40% 内容。v9 加入前置分流器——简单任务根本不走完整流程，从根本上减少了需要兼容的场景。

**可迁移教训**：规则的数量不是线性增长的——N 条规则之间有 N(N-1)/2 种潜在冲突。加规则的边际成本递增。

---

## 失败 2：Agent 产出没存文件，下一轮找不到了

**发生了什么**：理论文档协作任务中，Writer Agent 产出的 v3.0 只存在于 Agent 的对话上下文里，没有存文件。下一轮需要参考 v3.0 时，新派的 Writer Agent 说"我找不到 v3.0 的源文件"——被迫重新派 Agent 从头来。

**为什么错**：没有意识到 Agent 的对话上下文是"一次性"的。一轮结束后上下文就丢了。调度员以为 Agent 的输出自然会被下一轮看到，实际上不是。

**怎么改的**：加入硬规则："Agent 产出后续要用 → 必须先存文件。对话里的输出下一轮 Agent 看不到。"

**可迁移教训**：跨上下文的信息传递必须走持久存储（文件），不能依赖"在同一个对话里"。这在任何分布式系统里都成立。

---

## 失败 3：隐性依赖导致并行 Agent 出错

**发生了什么**：在系统架构任务中，审计员和架构师被同时并行派出。但审计员的发现应该影响架构师的设计——审计员指出的问题恰好是架构师应该解决的。因为并行了，架构师在不知道审计结果的情况下完成了设计，导致设计包含了已经被审计员否决的方案。

**为什么错**：选角色时没有检查"A 的产出会不会影响 B 的输入"。只看了"两个 Agent 没有直接依赖"就判断可以并行，忽略了"信息依赖"。

**怎么改的**：加入硬规则："并行前必须检查隐性依赖——'这个 Agent 的产出会不会影响另一个 Agent 的输入？'会的话必须串行。"

**可迁移教训**：并行不只是"没有执行依赖"就可以，还要检查"信息依赖"。这个教训在任何并行系统设计中都适用。

---

## 失败 4：经验写了不用（最普遍的问题）

**发生了什么**：memory 文件里积累了十几条经验教训，但每次启动新任务时并没有读取或使用它们。经验静静地躺在文件里，跟没有一样。用户指出："你自己针对 skill 和经验的提升我目前还没看到。"

**为什么错**：把"写经验"当成了终点，没有建立"读经验→转化→执行"的闭环。经验是被动存储，不是主动注入。

**怎么改的**：
- v10：第1步读经验时要求"转化为决策检查点"
- v11：加了具体转化格式（"本次必须检查：[在什么节点][检查什么][如果发现怎么处理]"）
- 反模式新增第15条："读了经验不转化"

**可迁移教训**：知识管理系统的核心问题不是"怎么存"，而是"怎么用"。存了不用 = 没存。

---

## 失败 5：过度包装被批评家拆穿

**发生了什么**：在技术总结时，把 6 个设计选择称为"创新机制"，跟 AutoGen/CrewAI/LangGraph 做功能对比，暗示对等关系。批评家审查后指出：(1) 一个 .md 文件跟 Python 框架不对等（范畴错误）；(2) 至少 4 个"独特"机制竞品也有类似能力；(3) 竞品数据基于训练集，不可靠。

**为什么错**：为了"展示价值"而过度声称。把"好的设计选择"包装成"独创创新"，把"不同的东西"包装成"更好的东西"。这是自信变自大的典型路径。

**怎么改的**：
- 措辞降级："创新机制"→"核心机制设计"，"独特"→"差异点"
- 加定位声明：开头明确说"这是一个 .md 文件，不是框架"
- 加置信度标注：每条对比结论标 [已验证]/[待确认]/[推测]

**可迁移教训**：诚实是最好的策略。说"这是我们的设计选择，不一定独创但有参考价值"比说"我们独创了6个创新机制"更容易获得认可——因为前者经得起追问，后者一追问就穿帮。
