# Multi-Agent 协作调度方法论：技术总结

> **定位声明**：这不是一个独立运行的软件框架（没有代码库、没有 SDK），而是一套在 Claude Code 上运行的多 Agent 协作调度方法论，通过一个 slash command（`.md` 文件）实现。核心价值是方法论设计（分流→分工→对抗→验收→进化），不是代码。

## 方法论概述

解决单 Agent 处理复杂任务时视角单一、缺乏对抗审查、容易目标漂移的问题。三层机制：

1. **前置分流器**：3 个 yes/no 问题将任务分为极简/框架/探针三种模式，简单任务不走完整流程
2. **执行中**：信号驱动的动态角色引入 + 强制对抗审查（批评家必须存在）
3. **任务后**：复盘经验回写 memory，下次自动注入

完整流程：分流 → 读经验→读现场→拆解 → 计划审查 → Wave 调度（并行/串行） → 每轮验收闭环 → 全局审视 → 验证→交付→复盘→经验沉淀

## 核心设计选择（6 个机制）

| 机制 | 解决什么问题 |
|---|---|
| 前置分流器 | 简单任务被过度工程化 |
| 信号驱动角色引入 | 角色膨胀、上下文开销 |
| 经验→决策检查点转化 | "经验写了不用等于没写" |
| 强制对抗 + 第二批评家兜底 | 审查走过场 |
| 服务对象视角内置验收 | 传统验收只查需求满足、不查使用者体验 |
| 每轮验收闭环 | 最后才验一次→偏差积累 |

详细设计见 `commands/multi-agent.md`（skill 主文件，约 500 行）。

## 实战验证

### A/B 实验（pilot study，3 组对照）

| 任务 | 分流器 | 核心差异 |
|---|---|---|
| *args/**kwargs 区别 | 极简模式，正确跳过 | 产出等价，分流器通过极限测试 |
| 代码解释+找问题 | 极简模式，正确跳过 | 多发现 1 个边界问题（布尔值比较陷阱） |
| 多人协作文档冲突方案 | 框架模式，启动多 Agent | 批评家找到 2 个严重问题（时钟因果链断裂、客户端缓存缺失），对照组未发现 |

**核心发现**：分流器全场景正确；价值不在"产出更多"，在"找到对照组漏掉的问题"——批评家是 MVP。

### 跨模型验证（MiMo + DeepSeek，预埋 bug 法）

6 个任务（3 中等 + 3 复杂），每任务预埋 3 个 bug，满分 54 分。每个条件全新空白对话，零上下文污染。

| | MiMo (Claude) | DeepSeek |
|---|:---:|:---:|
| 无 Skill | 0/54 | 0/54 |
| 有 Skill | **9/54** | **10/54** |

核心发现：无 Skill 基线跨模型一致为 0（LLM 默认不质疑设计）；批评家增量集中在竞态条件、状态机漏洞、攻击面推演；两个模型审查能力在同一水平。

详见 `evaluation/FINAL_REPORT.md`。

### 实际使用案例

- **CLI 工具开发**：批评家发现 2 个 bug，产出偏长→改为先给结论再展开
- **理论文档协作**：4 轮迭代从学术框架到可操作指南，场景测试员发现文科生入口缺失
- **经验数据**：13 条任务经验提炼——做减法比加法重要、假分工是最危险的反模式、闭环没接上等于白做

详见 `examples/cases.md`。

## 方法论演进

从 v1（334 行膨胀）到 v12.5（约 500 行冻结），12 个版本迭代：

- v1→v4：砍掉 40% 内容，发现"角色职责重叠"和"流程自相矛盾"
- v9：加前置分流器——结构性减法，简单任务不走完整流程
- v11：经验→决策检查点转化，从"做了好"到"不做不行"
- v12.5：冻结等数据——AI 没有"够了"的感知，人类在 AI 工程中最重要的角色是喊停

详见 `docs/framework_methodology.md`。
