# 多Agent框架构建方法论：从0到v12.5的反思迭代实录

> 这不是一份使用指南，而是一份构建指南。你不需要照搬我们的skill，但可以借鉴我们踩过的坑。
> 所有案例来自真实任务记录，数据可追溯到 memory 文件的100+条经验日志。

---

## 1. 从0到1：第一版为什么失败

v1写了334行，塞进了所有能想到的机制：固定角色池、写死的流程步骤、堆叠的规则。写完发现两个致命问题：

- **角色职责重叠**："批评家"和"代码审查员"到底谁负责找问题？没有答案，因为设计时没想过这个问题。
- **流程自相矛盾**：某个步骤要求并行，另一个步骤要求串行但没说明跟谁串行。

v2又加了一层"系统边界+用户交互协议"，结果是更复杂。v3才意识到应该"动态生成角色"而非从模板选取。到v4被迫大砍刀——334行砍到208行，近40%内容删除。

**教训**：N条规则之间有N(N-1)/2种潜在冲突。加规则的边际成本递增。第一版应该是"能跑的最简版本"，不是"想到的全部功能"。

**怎么应用**：写第一版时问自己"如果只能保留3条规则，保留哪3条？"这3条就是核心，其他都是锦上添花。

---

## 2. 做减法比加法重要

v4精简后，v5又补回了一些被误删的关键内容（硬约束、复盘格式、任务类型映射）。这个"砍→补"循环说明：

- **减法不是一刀切**，而是区分"核心机制"和"衍生规则"。核心机制（如强制对抗、需求锚定）不能砍；衍生规则（如角色命名规范）可以后补。
- **v9的前置分流器**才是真正的结构性减法——不是砍规则，而是让简单任务根本不走完整流程。分流器用3个yes/no问题把任务分成极简/框架/探针三种模式，从根本上减少了需要兼容的场景。

A/B实验证明分流器正确：最简单的事实性问题（Task A）正确触发极简模式，跳过全部流程，产出和对照组等价。如果极简任务下实验组比对照组丰富3倍，反而是分流器失败。

**怎么判断该砍什么**：如果一条规则和另一条规则在实际执行中从未被同时触发，说明它们覆盖的是不同场景——考虑用分流器把场景分开，而不是让同一条流程兼容所有场景。

## 3. 让规则变硬：从"加规则"到"装传感器"

这是整个迭代中最重要的发现。

doc-pipeline任务暴露了5个缺陷，每个都能映射到skill中已有的规则——但对应的规则都没被执行：

| 缺陷 | 映射的规则 | 为什么没执行 |
|---|---|---|
| `force_fonts`变量名错误 | 反模式#15（读了经验不转化） | 靠调度员记忆 |
| Agent声称改了文件但没改 | Agent产出验证规则 | 没有强制检查点 |
| `cn_heading`定义未用 | 红线#4（目标漂移） | 没有在流程中触发 |
| Token检查漏环境变量 | 模拟用户经验 | 没有硬化为checklist |
| `grep -P`不跨平台 | 跨平台感知经验 | 只是建议，不是前置检查 |

**核心结论**：规则写得对但没有"强制执行点"——大多数靠调度员记忆执行，不是靠流程强制。

**"装传感器"的3个具体路径**：

1. **流程级**：把规则嵌入执行步骤，跳过=流程未完成。比如"Agent产出写文件后→主AI必须Read验证"，这不是加新规则，是改变执行流程。
2. **步骤级**：把建议硬化为checklist。比如验收者从"应该每轮出场"变成Step 3的强制checklist，不做=本轮未完成。
3. **命令级**：把检查变成前置动作。比如Bash命令前检查跨平台兼容性，不是事后发现`grep -P`在macOS上炸了。

**怎么识别"看起来有效但实际没用"的规则**：让另一个Agent（审计员）只看客观执行痕迹（tool calls、文件变更），不看调度员的自检声明。如果规则存在但执行痕迹中找不到对应动作，这条规则就是装饰品。

## 4. 对抗审查：为什么它是MVP

A/B实验中唯一有对照数据的Task C（复杂方案设计），实验组批评家找到了2个对照组遗漏的严重设计漏洞：

- **Lamport时钟因果链断裂**：对照组给了Lamport时钟方案但没人质疑因果链完整性。实验组：架构师选Lamport→批评家挑战→改为Hybrid Logical Clock。
- **客户端缓存缺失**：对照组方案自洽但没质疑自己的缓存策略。

对照组的设计不差——数据模型有Branch概念，覆盖了全部4个约束，比实验组更简洁。但**对照组不会质疑自己的设计选择**——这是单Agent做复杂决策时的结构性盲区，不是能力问题。

**什么时候批评家没用**：极简任务（Task A/B）。分流器正确判极简模式，跳过全部流程。极简任务不需要对抗审查。

**怎么判断要不要派批评家**：不是看"有没有代码"，而是看"这个决策有没有被质疑的可能"。分析/研究类任务也需要批评家——我们默认"分析不需要对抗审查"是错误的，批评家应该审查分析结论是否合理、是否有遗漏视角。

## 5. 经验闭环：从"写了不用"到"不用不行"

memory文件里积累了十几条经验教训，但每次启动新任务时并没有读取或使用。用户说："你自己针对skill和经验的提升我目前还没看到。"

经历了3个版本才解决：

| 版本 | 改动 | 效果 |
|---|---|---|
| v7 | 加"经验沉淀"机制（建议性） | 写了但不读 |
| v10 | 读经验时要求"转化为决策检查点" | 开始读但转化质量差 |
| v11 | 加具体转化格式+强制反思清单+反模式#15 | 从"做了好"到"不做不行" |

转化格式是关键——不是"读经验"，而是读完后写"本次必须检查：[在什么节点][检查什么][如果发现怎么处理]"。反模式#15明确：读了经验不转化=没读。

**三层内化**：(1)记忆层——写入memory文件 (2)文件层——在产出文件中体现教训（如技术总结用"设计思路"而非"重要性"）(3)行为层——下次遇到触发条件时执行新行为。只有第一层不算完成。

**怎么解决"写了不用"**：不要依赖"记得读"，要把"读→转化→执行"硬编码到流程第一步。并且用反模式明确标注"读了不转化=违规"。

## 6. 天花板判断：什么时候该停

理论文档任务（AI×生态位×注意力）经历了4轮迭代：

- Round 1：理论家+研究员并行，产出框架初稿
- Round 2：场景测试员发现入口缺失——文科生不知道从哪看起
- Round 3：需求锚定者发现概念联系薄弱——三个概念是并列的，不是循环的
- Round 4：场景测试员又发现文科盲区

Round 4后需求锚定者首次说"是"（需求已满足），到达天花板。

**判断规则**：每轮发现新问题=值得继续；每轮修同类问题=该停了。

**"换评估视角"比"重复同一视角"好**：Round 2用场景测试员、Round 3用需求锚定者、Round 4又用场景测试员——不同Agent看不同类型的盲区。如果每轮都让同一个批评家审查，它会重复提同类问题。

**AI的根本局限**：Claude没有"够了"的内置感知，会一直优化直到被外部力量叫停。v1到v12.5加了12个版本，skill自己违反了自己的"做减法比加法重要"原则。人类在AI工程中最重要的角色不是设计框架，是在对的时候喊停。v12.5的冻结决定本身是这个项目最关键的"硬机制"。

**怎么判断天花板**：不要只看"有没有新问题"，还要看"新问题的严重程度是否在下降"。如果Round 1发现致命问题、Round 4发现的是措辞建议，边际收益已经很低了。

## 7. 可迁移教训

以下教训不只适用于多Agent框架，适用于任何AI辅助工程：

**"先读现场再拆解"**——工程任务不读代码就派Agent，等于在信息不足时做决策。这对应人类开发中的"先读代码再开写"。

**"闭环没接上等于白做"**——复盘纪要中的改进建议如果不回写到持久存储，下次任务启动时就丢失了。任何知识管理系统的核心问题不是"怎么存"，而是"怎么用"。

**"做技术总结时先做定位声明"**——"这是什么"比"这有多好"重要。doc-pipeline的批评家指出：一个.md文件不应该跟Python框架做功能对比。定位错误导致后续所有对比都跑偏。

**"分析了不写下来=没分析"**——每次审视完必须立即写入持久文件。这是"做事→交付→等下一个任务"的默认模式缺少"做事→反思→内化→自动用上"闭环的同源问题。

**"有隐性依赖的不能并行"**——并行不只是"没有执行依赖"就可以，还要检查"A的产出结论是否影响B的设计选择"。这在任何分布式系统设计中都适用。

## 8. 给想自己搭框架的人的建议

1. **从最简版开始**。你的v1应该只有3条规则：谁对抗谁（执行者≠审查者）、怎么验收（对照原始需求）、什么时候停（信号驱动而非固定轮次）。其他都是衍生。

2. **先做分流器**。不是所有任务都需要完整流程。3个yes/no问题就能把任务分成"直接做"和"走流程"两类。这比优化流程本身更有价值。

3. **区分"加规则"和"装传感器"**。规则写了不执行等于没写。问自己：这条规则违反时，有没有任何客观痕迹能被检测到？如果没有，这条规则就是装饰品。真正的硬机制需要嵌入执行流程，不依赖记忆。

4. **派审计员审查自己**。用你的框架审查框架本身——这不是meta游戏，而是验证机制是否真的被执行的唯一方法。审计员只看客观痕迹（tool calls、文件变更），不看自检声明。

5. **攒够验证数据再迭代**。v1到v12.5加了12个版本，但从没跑够任务验证"加的东西有没有用"。冻结后先跑5-10个任务，用数据决定保留/砍掉/改进。没有数据支撑的改进都是猜测。

6. **人类最重要的角色是喊停**。AI没有"够了"的内置感知。框架设计中最关键的决策往往不是"加什么"，而是"什么时候不加"。
