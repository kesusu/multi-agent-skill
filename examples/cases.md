# 使用样例

以下是 multi-agent skill 的实际使用记录。每个样例记录：任务类型、分流结果、角色配置、关键发现。

---

## 1. A/B 对照实验（验证分流器 + 对抗审查）

### Task A：极简事实问题
- **任务**：Python 的 `*args` 和 `**kwargs` 有什么区别？
- **分流结果**：极简模式（Q1=答案, Q2=是, Q3=不大）
- **表现**：分流器正确判极简，直接回答，跳过全部流程。对照组产出等价。
- **结论**：分流器在极端简单任务上正常工作。

### Task B：中等代码审查
- **任务**：解释一个 Python 函数并找出潜在问题
- **分流结果**：极简模式
- **表现**：实验组找到 4 个问题（对照组 3 个），多出的是布尔值比较陷阱 `True > 0`。
- **结论**：微小差异，分流器判定正确。

### Task C：复杂方案设计 ★ 核心验证
- **任务**：设计一个多人协作文档的冲突解决方案
- **分流结果**：框架模式
- **角色配置**：架构师 + 批评家 + 验收者
- **关键发现**：批评家找到 2 个对照组遗漏的严重设计漏洞（HLC 因果链断裂 + 客户端缓存缺失）。对照组设计方案自洽但未质疑自己的设计选择。
- **结论**：**强制对抗审查是目前唯一经过验证的核心价值。** 单 Agent 做复杂决策时不会质疑自己——这是结构性盲区，不是能力问题。

**自己试一下**：
```
/multi-agent 设计一个多人协作文档的冲突解决方案。约束：10人同时编辑、离线5-30分钟、版本历史+回滚、自动合并。
```

## 2. 愤怒的小鸟（工程实现 + 物理调试）

- **任务**：单文件 HTML 愤怒小鸟游戏，含 2D 物理引擎、关卡系统、音频
- **分流结果**：框架模式
- **角色配置**：架构师 + 执行者 + 测试员 + 批评家
- **成品文件**：`demos/angry_birds.html`（单文件，910 行，浏览器直接打开即可玩）

**自己试一下**：
```
/multi-agent 用纯 HTML+JS 写一个愤怒的小鸟游戏。要求：3个关卡、弹弓发射、2D物理（重力+碰撞+弹性）、小鸟有不同技能、有音效。
```
- **关键发现**：
  - 物理引擎子步进是防穿模的基础（每帧 8 个子步）
  - Canvas 渲染中不能用 `rand()`——每帧重绘时产生不同值导致闪烁
  - 伤害参数必须和物理参数联动校准
  - 同一 bug 修了 8+ 暴露了"没有硬性叫停机制"的结构性问题
- **经验产出**：8 条游戏开发相关经验（写入 memory）
- **教训**：跳过了独立审查环节（违规）；默认"功能能跑"不关注"体验好不好"

## 3. AI × 生态位 × 注意力 理论文档（理论探讨 + 写作）

- **任务**：撰写 AI 时代大学生定位理论框架文档
- **分流结果**：框架模式
- **角色配置**：理论家 + 研究员 + 批评家 + 验收者 + 场景测试员
- **文件**：`ai_theory/theory_v3.2.md`（通用版）+ `ai_theory/theory_v3.2_cs.md`（CS/EE 专属版）
- **关键发现**：
  - "生态位"的正确理解不是"AI 不行的地方"而是"你天然知道让 AI 往哪走的方向感"
  - AI × 生态位 × 注意力是循环放大器不是并列能力
  - 文档逻辑流必须遵循依赖链：概念在被引用之前定义
  - 缺少"服务对象视角"——没有从读者能不能看懂出发检查
- **经验产出**：6 条写作/理论类经验
- **迭代轮次**：4 轮（需求锚定者首次说"是"时到达天花板）

## 4. doc-pipeline（Skill 开发 + 流程验证）

- **任务**：扫描 PDF 转可编辑 Word 的 pipeline skill
- **分流结果**：框架模式
- **文件**：`~/.claude/commands/doc-pipeline/`
- **关键发现**（5 个缺陷 → 5 条规则映射）：
  1. `force_fonts` 变量名错误 → 反模式#15 没执行
  2. Agent 声称改了文件但没改 → Agent 产出验证规则没执行
  3. `cn_heading` 定义未用 → 红线#4 目标漂移没检查
  4. Token 检查漏环境变量 → 模拟用户经验没执行
  5. `grep -P` 不跨平台 → 跨平台感知经验没执行
- **核心价值**：第一份"规则正确但没执行"的实证数据。证明了规则设计方向对，但"硬度"不够——大多数靠调度员记忆执行，不是靠流程强制。
- **直接产出**：3 个流程级"装传感器"改动（Agent 产出验证、验收 checklist 硬化、跨平台检查）

## 5. 多 Agent 自审查（用 skill 审查 skill 自身）

- **任务**：用多 Agent 框架审查 multi-agent skill 本身的规则执行情况
- **关键发现**：
  - 首次审计：4/8 通过，发现 2 个真实违规（没派批评家、教训没写入持久文件）
  - 自检全是自我参照——审计员如果只看调度员材料也是假独立
  - 审计机制有效：确实 catch 到了调度员自己不会承认的违规
- **经验产出**：3 条关于审计机制的经验
- **意义**：验证了"用多 Agent 解决多 Agent 自身的问题"是有效的，但也暴露了架构局限——所有 Agent 都是调度员派的，不存在"真正独立"的审计主体

## 样例选择说明

以上 5 个样例覆盖了 skill 的主要使用场景：

| 样例 | 验证了什么 |
|---|---|
| A/B 实验 | 分流器准确性 + 对抗审查价值 |
| 愤怒的小鸟 | 工程实现类任务 + 物理调试 + 长链迭代 |
| 理论文档 | 理论探讨/写作类任务 + 多轮迭代 + 天花板判断 |
| doc-pipeline | 规则执行验证 + "装传感器"方法论 |
| 自审查 | 审计机制有效性 + 框架自我验证 |

注意：这些是单人单次执行的数据，不是跨用户验证。A/B 实验 Task C 是唯一的对照数据点（样本量 1）。其余样例展示的是 skill 在不同任务类型上的实际运作方式，不是效果验证。
