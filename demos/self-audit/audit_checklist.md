# AI 工作流审计清单（8 项检查）

> 不检查"做得好不好"，检查"声称做了的事是否真的做了"。

## 使用说明

任务完成后逐条检查。每条判定 pass/fail，必须引用具体证据。无证据的判定为"不合规"。

**环境说明**：第 1/2/6/8 项适用于任何 AI 辅助工作流。第 3/4/5/7 项需要多 Agent 环境（如 Claude Code 的 Agent 工具），单 Agent 场景下可以跳过这些。

## 检查清单

| # | 检查项 | 适用环境 | 检查方法 | 为什么重要 |
|:---|:---|:---|:---|:---|
| 1 | 经验是否转化为检查点 | 通用 | 任务计划中"经验"字段是否含具体检查动作 | 读了经验但不转化 = 没读 |
| 2 | 是否先读现场再拆解 | 通用 | 对话中是否在拆解前读了相关文件/代码 | 不读上下文就派任务 = 信息不足时做决策 |
| 3 | 对抗角色是否被派出 | 多 Agent | 对话中是否有独立审查者的调用记录 | 没人质疑 = 自己做决定自己查 |
| 4 | 验收者是否出场 | 多 Agent | 对话中是否有验收者的调用记录 | 中等以上任务每轮需要验收 |
| 5 | 因果链是否维护 | 多 Agent | 是否有记录：哪个批评→触发了什么改动→导致了什么下游变化 | 超 2 轮迭代不记录 = 无法追溯决策 |
| 6 | 用户暂停信号是否被响应 | 通用 | 用户说"停/怎么回事"时是否暂停并汇报 | 不响应暂停信号 = 忽略用户控制权 |
| 7 | 修复计数器是否非自我维护 | 多 Agent | 计数器维护者是否为非执行者（裁判不能兼运动员） | 修 bug 的人自己计数 = 永远不会触发强制停机 |
| 8 | 决策/教训是否写入持久文件 | 通用 | 汇报前是否有文件写入动作 | 在对话里分析完就算做了 = 下次丢失 |

## 单 Agent 场景的简化版

如果不用多 Agent 框架，用这 4 项就够了：

1. **读了经验有没有转化为行动？** — 读完教程/文档后，写出"本次我要检查：X、Y、Z"
2. **动手前有没有读上下文？** — 改代码前先看相关文件、测试、配置
3. **用户说停的时候停了吗？** — 不要自顾自继续
4. **教训写下来了吗？** — 踩过的坑不写下来，下次还会踩

## 关键洞察

### "自检全 pass"是最可疑信号

如果自我检查全部通过，大概率是检查不够认真。在多 Agent 环境中，引入独立审计员——它读客观执行痕迹（tool calls、文件变更、Agent 调用记录），忽略自检声明。

### "加规则"不如"装传感器"

规则写得对但没有强制执行点 = 没写。判断一条规则是否有效：**违反时有没有任何客观痕迹能被检测到？** 如果没有，就是装饰品。

三个硬化路径：
- **流程级**：嵌入执行步骤，跳过 = 流程未完成
- **步骤级**：硬化为 checklist，不做 = 本轮未完成
- **命令级**：变成前置动作，不是事后检查

### 用客观痕迹而非主观声明做验证

不要看 AI 说"我做了什么"，看 tool calls、文件变更、输出产物。这个原则不依赖任何框架，单 Agent 场景下用户自己就可以做——比如让 AI 改完代码后，自己 `git diff` 看改了什么，而不是听 AI 说"我改好了"。

## 诚实局限

审计员不能消除作弊——在多 Agent 框架中，所有 Agent 都是调度员派的，prompt 和输入由调度员控制。审计机制的价值是**提高敷衍/造假的成本**：调度员需要伪造整个对话痕迹（Agent 调用记录、tool results、文件变更），而不只是在自检里写"已执行"。

更根本的局限：`.md` 文件的规则是语义约束而非程序约束。AI 每次调用重新读一遍，没有状态记忆。所有"必须""禁止"都依赖"碰巧做对"，不依赖强制。真正的硬机制只能通过 hooks/settings.json/脚本实现。
