# AI 工作流审计 — 用客观痕迹代替主观声明

> 核心思想：不看 AI 说"我做了什么"，看 tool calls 和文件变更。

## 这是什么

用独立的 AI（审计员）审查另一个 AI 的工作是否真的按规则执行了。审计员读客观执行痕迹——tool calls、文件变更、Agent 调用记录——逐条判定 pass/fail，每条必须引用具体证据。

**不是**：AI 自己检查自己。**是**：一个独立的 AI 读执行痕迹，检查另一个 AI 是否真的做了它声称做的事。

## 为什么需要

AI 的默认模式：做事 → 交付 → 等下一个任务。更关键的是：**AI 写了规则但自己不执行。**

实际案例：doc-pipeline 任务中发现 5 个缺陷，每个都能映射到已有规则，但对应的规则都没被执行。规则写得对，但没有强制执行点 = 没写。

## 审计怎么工作

### 双层结构

**第 A 层：自我检查（3 项）**
- 审计材料是否准备好
- 上轮 fail 项是否已补救
- 本轮审计是否被跳过

这一层本质上仍是自我声明——但它是必要的前置步骤。

**第 B 层：独立审计（核心）**

审计员的输入是**完整对话上下文**（所有 tool calls、文件变更），而非自检报告。关键指令：**忽略自检声明，只依据客观痕迹判定。**

每条判定必须引用具体证据（如"对话第 X 轮未见审查者调用记录"）。无证据 = 不合规。

### 触发条件

| 条件 | 行为 |
|:---|:---|
| 自检全 pass | **必须触发** — 全 pass 是最可疑信号 |
| 跳过自检 | 立即触发 |
| 累计 ≥ 3 轮 | 每轮触发 |
| 用户含质疑信号 | 必须触发 |

## 实际案例：开源前诊断报告

[`diagnostic_report.md`](diagnostic_report.md) 是审计机制的一次实际产出——2026-05-28 用 3 个独立 Agent 并行审查了 multi-agent skill 的开源准备度。

**它证明了什么**：
- 审计能发现自检发现不了的问题（11 项声称中 3 项有问题，自检时全部标为"已确认"）
- 审计能发现自己不会承认的低估（5 个机制被 README 低估了，包括计划审查 Agent 和策略批评模式）
- 审计不会胡乱吹牛（结论是"没有吹牛，但仓库层面粗糙"，不是"一切都好"）

**它不能证明什么**：
- 不能证明审计机制在所有场景下有效（单次数据点，不是统计结论）
- 不能证明审计员"真正独立"（所有 Agent 都是调度员派的，见下方局限）

## 可迁移洞察

### 1. 分流器：先判断要不要走流程

3 个 yes/no 问题判断任务复杂度：
1. 用户要的是"一个答案"还是"一套方案"？
2. 这件事是否简单？
3. 搞错了代价大不大？

简单任务直接做，不走流程。**先判断要不要走流程，再优化流程本身。** 这个思想适用于任何工作流设计。

### 2. 对抗审查：复杂决策的 MVP

A/B 实验中，单 Agent 设计了一个多人协作文档方案——方案自洽，但没人质疑设计选择。批评家（独立审查者）找到了 2 个严重漏洞：
- Lamport 时钟在网络分区重连后因果链会断裂 → 改为 HLC
- 方案缺少客户端缓存层，离线用户每次操作都要全量请求

**核心发现**：单 Agent 做复杂决策时的结构性盲区不是能力问题，是**不会质疑自己的设计选择**。任何需要高质量决策的场景都值得引入一个"反对者"。

### 3. 人类最重要的角色是喊停

AI 没有"够了"的内置感知——它会一直优化直到被外部力量叫停。这个框架从 v1 到 v12.5 迭代了 12 个版本，违反了自己的"做减法比加法重要"原则。

**怎么判断该不该停**：
- 每轮发现新问题 = 值得继续
- 每轮修同类问题 = 该停了
- 同一问题连续 2 轮没改善 → 先定位根因（方案缺陷还是执行缺陷？），不要盲目继续

冻结决定本身是这个项目最关键的"硬机制"。

### 4. 经验闭环的三层内化

1. **记忆层** — 写下来（"我学到了 X"）
2. **文件层** — 在产出中体现（"我的代码/文档里体现了 X"）
3. **行为层** — 下次遇到触发条件时执行新行为（"下次遇到 Y，我做 Z 而不是 W"）

只有第一层不算完成。转化格式是关键：不是"读经验"，而是读完后写"本次必须检查：[在什么节点][检查什么][如果发现怎么处理]"。

## 诚实局限

### 审计员不是真正独立的

在多 Agent 框架中，所有 Agent 都是调度员派的，prompt 和输入由调度员控制。审计机制的价值不是消除作弊，而是**提高敷衍/造假的成本**——调度员需要伪造整个对话痕迹（Agent 调用记录、tool results、文件变更），而不只是在自检里写"已执行"。

### .md 文件的规则不是程序约束

AI 每次调用重新读一遍，没有状态记忆。所有"必须""禁止"都依赖"碰巧做对"，不依赖强制。真正的硬机制只能通过 hooks/settings.json/脚本实现。`.md` 文件能做到的上限是提高"碰巧做对"的概率。

### 不适用的场景

- **简单任务**（写个函数、改个配置）：审计成本 > 收益
- **没有多 Agent 环境**：检查清单的第 3/4/5/7 项需要多 Agent 支持（详见 [`audit_checklist.md`](audit_checklist.md)）
- **需要统计显著性验证的场景**：目前只有个案数据，不是大规模验证
