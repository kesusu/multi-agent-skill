# 单文件 HTML 修改规范

修改单文件游戏/应用时的依赖扫描、插入顺序、回归检查硬性规范。

## 规则 1：插入代码前必须做依赖扫描

**Why:** 单文件 HTML 的 `<script>` 是严格线性执行的。插入点之后定义的变量/函数/DOM 元素在插入点不可用。这不是可选项，是前置条件。

**How to apply:**
插入新代码块前，逐行检查：
1. 这段代码引用了哪些全局变量？它们在插入点是否已定义？
2. 这段代码引用了哪些 DOM 元素？它们在 `<body>` 中是否已在插入点之前出现？
3. 这段代码调用了哪些函数？它们是否已定义？

**自动验证**：可用 `python ~/.claude/rules/tools/scan_deps.py <html_file> <line> --check "code snippet"` 自动检测插入点前已定义/未定义的标识符。

**踩坑案例**：`canvas.addEventListener` 被放在 `const canvas=document.getElementById('game')` 之前 → ReferenceError → 页面白屏。

## 规则 2：加功能前审计关联系统的运行条件

**Why:** 新功能可能暴露已有系统的设计假设。两个看似无关的系统可能通过隐藏调用链关联。

**How to apply:**
当给游戏 A 系统加功能时，问：
1. 我的新功能会不会触发 B 系统的行为？
2. B 系统在哪些条件下运行？
3. 我的功能触发 B 行为时，B 系统处于什么状态？那个状态下它能正确处理吗？

**踩坑案例**：加爆炸音效 → 爆炸效果施加物理力 → 物理只在 FLY/SETTLE 运行 → SETTLE_TIME 2.5s 不够高空猪落地 → 强制结算时猪还在天上。

## 规则 3：状态机完整性审计

**Why:** 每个实体在每个游戏状态下都需要被正确处理。遗漏任何组合都是潜在 bug。

**How to apply:**
画实体×状态矩阵，标记每个交叉点是否被正确处理：

| 实体 \ 状态 | WAIT | FLY | SETTLE |
|---|---|---|---|
| 鸟 | 固定在弹弓 | 重力+碰撞 | 静止 |
| 猪 | ❓ | 重力+碰撞 | 重力+碰撞 |
| 方块 | ❓ | 重力+碰撞 | 重力+碰撞 |

标 ❓ 的就是需要决策的地方。不做这个矩阵 = 不知道有没有盲区。

## 规则 4：交付前自测核心路径

**Why:** 用户第一次打开页面就白屏，信任直接归零。任何改动都必须经过最小验证。

**How to apply:**
交付前走一遍：
1. 打开页面 → 白屏？JS 控制台有错？
2. 选关卡 → 能进游戏？
3. 核心操作 → 正常？
4. 重试/返回 → 状态干净？资源清理？
5. 边界路径 → 也能跑通？

**精简版**：写完代码后，不要告诉用户"完成了"，而是"写完了，我在验证"。
