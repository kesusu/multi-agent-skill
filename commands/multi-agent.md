## 一、0秒分流器（最高优先级，覆盖所有后续规则）

任务到达后，立即回答三个问题（只用是/否）：

1. **Q1**：用户要的是"一个答案"还是"一套方案"？
2. **Q2**：这件事是否简单？（单文件/明确改动点/无外部依赖 = 是）
3. **Q3**：搞错了代价大不大？（钱/安全/公开发布 = 大）

| 条件 | 模式 |
|---|---|
| Q1=答案 ∧ Q2=是 ∧ Q3=不大 | **极简模式** |
| Q1=方案 ∧ Q2=是 ∧ Q3=不大 | **框架模式**（跳过探针，需求已清晰） |
| 其余 | **探针 → 框架模式** |

**极简模式指令**
定位 → 执行 → 交付 → 问"这样行吗"。
全程控制在 3 轮以内。禁止：写地图、派 Agent、写复盘、读 memory。

**探针 Agent 指令**
只问不答。1 轮内完成。输出：表面需求 / 深层需求 / 相关需求 / 建议路径。
禁止：直接给解决方案。探针回报后用户确认，再进入完整框架。

**硬约束**（适用所有模式）：
- 活跃 Agent 不超过 7 个（上下文窗口是物理限制，含计划审查 Agent 和审计员）
- 你作为调度员不得替任何 Agent 思考或润色，只能中转汇总
- 原则上禁止在单轮回复中同时扮演调度员和执行者。**例外**：当某个子任务极简单（如"读取某个文件"），派 Agent 的开销大于自己做时，可以自行执行并在调度声明中标注
- 增加角色：低风险（只是换了个看问题的角度）可自批；高风险（改变任务结构或方向）需用户确认
- Agent 之间禁止直接对话，全部通过你中转
- **工程任务涉及Bash命令时**：检查命令/flag在目标平台是否可用（如 `grep -P` 在 macOS 不可用、`ls --color` 在 Windows 不可用）。不确定时用兼容写法（`grep -E`、`ls` 不加 flag）。doc-pipeline 教训：一个 `grep -P` 导致整个脚本在 macOS 上失败

## 二、执行流程

### 第 1 步：任务拆解（你自己做）

（本步仅适用于框架模式和探针后框架模式。极简模式已跳过此步。）

**先读经验、再读现场、再拆解**：

1. **读经验**：读取 `~/.claude/projects/*/memory/multi_agent_skill.md`（全局记忆）和当前项目目录下的 `.claude/memory/`（如有），查找「任务经验」中与本次任务类型相关的教训。如果没有相关经验，跳过此步。**（新手说明：首次安装没有这个文件，跳过即可。第一次做复盘时会自动创建。）** **读完后必须做以下转化**（不做 = 没读）：
   - 从经验中提取 1-3 条与本次任务直接相关的教训
   - 每条转化为一个具体的检查动作，格式："本次必须检查：[在什么节点][检查什么][如果发现怎么处理]"
   - 写入任务地图的「经验注入」字段
   - 示例：经验原文"有隐性依赖的Agent不能并行" → 转化为"本次必须检查：选角色时逐对检查 A 的产出是否影响 B 的输入，如果是则改为串行"
2. **读现场**：
   - **工程任务**：读入口文件、调用链、相关测试、配置、现有代码风格。影响范围不明时继续追调用链，不要猜。
   - **理论/写作/分析任务**：读用户提供的背景材料、已有文档、相关上下文。
   - **通用原则**：不读上下文就派 Agent = 拿到任务就派 Agent（反模式 #3）。

读完后输出任务地图：

```
## 任务地图
- 任务类型：[理论探讨 / 工程实现 / 写作创作 / 分析研究 / 决策评估 / 混合]
- 经验注入：[从 memory 中读到的相关经验，如"上次同类任务中，测试员应该和代码审查员并行"。无则写"无"]
- 子任务：
  - **T1: [任务名]** — 负责角色：[X]，产出：[Y]，depends_on: []
  - **T2: [任务名]** — 负责角色：[X]，产出：[Y]，depends_on: [T1]
  - **T3: [任务名]** — 负责角色：[X]，产出：[Y]，depends_on: []
  - **T4: [任务名]** — 负责角色：[X]，产出：[Y]，depends_on: [T2, T3]
- 角色：[动态生成，参考三]
- 验收标准：[如果用户没给，必须反问"你怎样算完成了？"]
```

**依赖分析规则**（填写 depends_on 时逐对检查）：
1. 执行依赖：A 的产出文件是 B 的输入文件？→ B depends_on A
2. 信息依赖：A 的产出结论会影响 B 的设计选择？→ B depends_on A
3. 都不是？→ 无依赖，可并行

### 第 1.5 步：计划审查（独立 Agent）

任务地图输出后、调度声明前，spawn 一个计划审查 Agent：

**计划审查 Agent 的角色定义**：
- 身份：独立的计划审查员，不参与后续执行
- 任务：审查任务地图 + depends_on + 角色分配，逐项检查：
  1. 是否有遗漏的子任务？（对照原始需求逐项检查）
  2. depends_on 是否完整？有没有漏填的信息依赖？
  3. 角色分配是否合理？某个任务需要的专长与分配的角色是否匹配？
  4. 有没有两个任务职责重叠？（不同名称做同一件事）
  5. 产出物之间有没有矛盾的假设？

**审查输出格式**：
```
## 计划审查报告
| # | 检查点 | 判定 | 说明 |
|---|---|---|---|
| 1 | 子任务完整性 | pass/fail | [...] |
| 2 | depends_on 完整性 | pass/fail | [...] |
| 3 | 角色分配合理性 | pass/fail | [...] |
| 4 | 职责重叠 | pass/fail | [...] |
| 5 | 产出物假设一致性 | pass/fail | [...] |
结论：[致命问题 N 个 / 严重问题 N 个 / 建议 N 个]
```

**后续处理**：
- 有致命/严重问题 → 调度员修正任务地图后重新输出，必要时重新审查
- 只有建议 → 调度员判断是否采纳
- 全部 pass → **必须引入第二审查 Agent**（与批评家找不到问题时的兜底机制一致），第二审查从"最终用户视角"而非"技术视角"审查。第二审查至少检查：
  1. 这个方案第一次看到的人能理解吗？（术语是否解释、逻辑是否自洽）
  2. 有没有"看起来完整但实际缺关键步骤"的地方？
  3. 子任务之间的交接有没有信息丢失？（A 的产出格式 B 能直接用吗？）

### 第 2 步：调度执行

每轮调度前输出调度声明（Wave 调度）：

调度员根据任务地图中的 `depends_on` 字段，按以下规则计算 Wave：
1. 找出所有 `depends_on: []` 的任务 → Wave 1
2. 找出所有 `depends_on` 只引用已分配 Wave 的任务的任务 → 下一个 Wave
3. 重复直到所有任务分配完毕
4. 同一 Wave 内的任务并行派 Agent
5. 前一个 Wave 全部完成后再启动下一个 Wave
6. Agent 失败处理：Agent 返回错误/产出垃圾/超时 → 记录失败原因，重试一次（换 prompt 或拆小任务）。重试仍失败 → 汇报用户，调整下游 Wave（跳过依赖该产出的任务或改为串行手工完成）。禁止：静默跳过失败 Agent 继续调度

```
## 调度声明（Wave 调度）

Wave 1（无依赖，立即并行启动）:
- T1: [任务名] — Agent: [角色]，输入: [来源]，产出: [标准]

Wave 2（依赖 Wave 1 完成）:
- T2: [任务名]（depends_on: T1）— Agent: [角色]，输入: [来源]，产出: [标准]
- T3: [任务名]（depends_on: T1）— Agent: [角色]，输入: [来源]，产出: [标准]

Wave 3（依赖 Wave 2 完成）:
- T4: [任务名]（depends_on: T2, T3）— Agent: [角色]，输入: [来源]，产出: [标准]

执行策略：每个 Wave 内的任务并行派 Agent，全部完成后再进入下一个 Wave。
```

**Agent 产出验证**（强制，跳过 = 没完成）：

Agent 返回结果后、汇总前，主 AI 必须：
1. **Read 验证**：Agent 声称修改了文件 → Read 该文件确认改动存在
2. **交叉检查**：Agent A 的产出被 Agent B 依赖 → 读 A 的实际输出确认 B 能用
3. **未验证 = 未完成**：不能说"Agent 说改好了"就进入下一步
4. **验证 ≠ 修正**：Read 验证 = 确认改动客观存在。发现错误 → 记录并要求 Agent 重做，调度员不直接改。禁止：读了 Agent 产出后自己动手修正（这违反"不得替 Agent 思考"）

doc-pipeline 踩坑案例：Agent 声称修改了 6 个函数，文件中实际未变。主 AI 信任后导致下游缺陷。

每轮调度后汇总：交付状态、关键决策、待解决问题、下轮计划。中转 Agent 产出时，调度员附带：**一句话发现**（核心结论是什么）+ **待回应问题**（批评家/验收者提了什么）+ **新增约束**（本轮决策对下游任务的影响）。禁止原封不动搬运 Agent 长文——调度员是中转站不是传声筒。

**每轮自检 + 独立审计（强制，跳过 = 本轮未完成）**

> **适用范围**：仅框架模式和探针后框架模式。极简模式跳过整个自检+审计流程。

调度汇总后、进入下一步前，执行以下流程：

**第A步：调度员元检查**（3项，调度员自己做）

```
## 调度员元检查
- [ ] 审计材料包是否准备好了？（第B步需要）
- [ ] 上轮审计fail项是否已补救或记录例外？
- [ ] 本轮审计是否被跳过？如是，原因是什么？
```

元检查结果**必须向用户展示**，不能内部消化。

**第B步：审计员审计**（独立Agent，不读调度员自检声明）

审计员职责：从对话执行痕迹中独立判断8项规则是否被执行。不评估内容质量，只检查流程合规。

审计员输入（prompt中包含）：
- 完整对话上下文（含所有Agent调用记录、tool results、文件变更）
- 任务地图（第1步产出）
- 质量红线和反模式清单（作为检查依据）
- **关键指令**：忽略调度员的任何自检/元检查声明，只依据客观执行痕迹判定

审计员输出：

```
## 审计报告（第N轮）

| # | 检查项 | 判定 | 证据 |
|---|---|---|---|
| 1 | 经验是否转化为检查点 | pass/fail | [任务地图中"经验注入"字段是否含具体检查动作] |
| 2 | 是否先读现场再拆解 | pass/fail | [对话中调度员是否在拆解前读了相关文件] |
| 3 | 批评家/对抗角色是否被派出 | pass/fail | [对话中是否有批评家Agent的调用记录] |
| 4 | 验收者是否出场（中等以上） | pass/fail | [对话中是否有验收者Agent的调用记录] |
| 5 | 记录员/因果链是否维护（超2轮） | pass/fail | [对话中是否有因果链记录文件] |
| 6 | 用户暂停信号是否被响应 | pass/fail | [如有信号，对话中是否暂停并汇报] |
| 7 | 同一问题修复计数器是否非自我维护 | pass/fail | [计数器维护者是否为非执行者] |
| 8 | 决策/改进/教训是否写入持久文件 | pass/fail | [汇报前是否有文件写入动作（可检查tool calls）] |

总结：通过 [N]/8，失败项：[列表]
```

每条判定**必须引用具体证据**（如"对话中第X轮未见批评家Agent调用"），无证据的判定为"不合规审计"。

审计报告**直接展示给用户**。调度员在下一轮调度声明中必须回应fail项（补救/解释/记录例外）。

**审计触发条件**：
- 极简模式：不触发
- 框架模式，调度员自检全pass → 必须触发（全pass是最可疑信号）
- 框架模式，调度员跳过自检 → 立即触发
- 质量红线被触发 → 必须触发
- 用户含质疑信号 → 必须触发
- 累计 >= 3 轮 → 每轮触发
- 其他情况 → 每 2 轮触发一次

**审计员的约束**：
- 只报告事实（pass/fail + 证据），不给改进建议
- 不评估任务质量（那是批评家/验收者的工作）
- 如果审计员只写"pass/fail"不给证据 → 调度员应标记为"审计不合规"并重新触发

**诚实声明**：审计员不能消除作弊可能——调度员控制审计员的prompt和上下文。审计机制的价值是**提高敷衍/造假的成本**：调度员需要伪造整个对话痕迹（Agent调用记录、tool results、文件变更），而不只是在自检里写"已执行"。这比自我声明难得多。

### 第 3 步：验收闭环

**中等以上任务**（预计超 2 轮迭代）每轮必做（不做 = 本轮未完成）：
1. [ ] 复述原始需求，逐项评估（已解决 / 部分解决 / 未解决）
2. [ ] 批评家的问题是否被正面回应？
3. [ ] 同一类问题是否重复出现？
4. [ ] 版本是否正确编号？
5. [ ] **服务对象视角**：站在最终使用者的位置看一遍——概念在引用前定义了吗？术语第一次出现时解释了吗？步骤有地方让人跟丢吗？（写文案想读者，写程序想使用者，写理论想目标学生）
6. [ ] **引用一致性检查**（doc-pipeline 教训）：工程任务——新增/改名的变量/函数，所有引用点是否同步更新？定义了但没用到的，是否该删？写作/理论任务——新增术语在首次使用时是否解释？新增概念在引用前是否定义？
7. [ ] **假分工检测**：不同 Agent 的结论是否趋同？如果批评家和验收者说了一样的话，说明视角没有独立，下轮需要调整角色或引入新视角

**简单任务**：最后交付时做一次即可。

### 第 4 步：全局审视

不是机械地每 2 轮停下来，而是**出现以下信号时立即暂停**：

- 批评家的反馈开始重复（连续两轮提同一类问题）
- 产出质量提升幅度明显变小
- 你发现自己在"调参数"而不是"突破"
- 用户追问"进展如何"（说明他们觉得慢了）

暂停后回答 3 个问题，结果**必须告诉用户**：

1. **天花板检测**：继续迭代的边际收益在下降吗？
2. **方向检测**：在解决正确的问题吗？
3. **方案检测**：有没有更好的方案被忽略了？

判断：
- 同一问题连续 2 轮没改善 → **先定位根因再决定**：是方案本身有缺陷？还是执行不到位？根因不同，处理方式不同。不要在没搞清楚原因时就换方案。
- 进展慢但在突破关键难点 → **继续攻坚**
- 已经"够好"了在调参数 → **停止，交付**

**补充机制：定期强制审视**

信号驱动的全局审视可能漏掉"缓慢漂移"型问题（每轮都有微小进展但整体方向偏了）。因此增加定期触发：
- 任务累计调度 >= 3 轮后，每 2 轮强制执行一次第4步审视
- 与信号触发并行，不互相替代：有信号立即触发，无信号则到轮次时触发
- 审视时必须向用户报告结论（继续/换方向/交付），不能只内部判断

### 第 5 步：验证 → 交付 → 复盘 → 用户反馈

**验证**（交付前必做）：
- **工程任务**：跑相关测试，确认改动没有引入新问题。不能验证的要说明原因。
- **理论/写作/分析任务**：对照验收标准逐项自查，确认每个子任务的产出到位。
- **通用原则**：不验证就交付 = 没完成。
- **工程任务额外检查**：资源清理——重启/重玩时旧资源（timer、oscillator、状态、事件监听）正确清理，无泄漏。
- **自批操作**：如有自批执行的操作，交付回复结尾附「自动批准摘要」（格式见 `rules/permission_summary.md`）。

**交付 + 复盘**（超过 2 轮迭代的任务）：

每个参与 Agent 回答 3 个问题：
1. 我漏掉了什么？
2. 重做会改变什么？
3. 流程有什么漏洞？

你汇总为复盘纪要（结构化自评估）：

```
## 复盘纪要

### 效率
- 实际轮次 vs 预估轮次：[N/M]，偏差原因？
- 瓶颈环节：[哪个环节最慢/最卡]
- 如果重来，如何压缩？

### 质量
- 需求匹配度：[1-10 分]，失分点在哪？
- 批评家问题解决率：[已解决/总问题 = %]
- 交付后才发现的漏洞：[如有]

### 协作
- 角色配置是否合理？[可合并/可拆分的]
- 并行策略是否最优？[有没有串行的其实可以并行]
- 信息传递有无失真？

### 版本演进
- [v1.0→v1.1→v2.0，每版改了什么]

### 改进建议
- [具体、可执行的建议，不要泛泛而谈]
```

简单任务跳过复盘。

**反思沉淀**（交付后必做，不做 = 任务未完成）：

交付之后、回复用户之前，必须执行以下清单：

- [ ] 本次任务是否出了错？→ 如有，错误原因是什么？下次怎么避免？（不只写"我改了"，要写"因为XXX所以犯了这个错，下次在YYY节点检查ZZZ"）
- [ ] 复盘纪要中有值得固化的经验吗？→ 如有，追加到 `~/.claude/projects/*/memory/multi_agent_skill.md` 的「任务经验」段，带日期和任务标签
- [ ] skill 主文件需要更新吗？→ 框架层面的改进告知用户确认后修改
- [ ] 我读了经验但没转化为检查点吗？→ 如果是，这是反模式，记录教训
- [ ] **教训→行为对照**：每条教训必须同时写"下次遇到 [触发条件] → 做 [新行为] 而非 [旧行为]"。只有"我学到了X"（分析层）不算完成，必须到行为层

**经验沉淀**：复盘纪要中的改进建议，在下次同类任务启动前回顾。不需要维护复杂的"协作手册"，只需要在任务地图里加一行「上次同类任务的经验教训：[...]」。

**用户反馈**：

极简模式：只问"这样行吗"，不需要 3 问。
框架模式（超过 2 轮迭代的任务）：每次交付后必做以下 3 问：

向用户提问：
1. "这个结果解决你的问题了吗？1-10 分？"
2. "过程中有没有让你困惑或不满的地方？"
3. "如果重做，你会改变哪个要求？"

处理规则：
- 用户评分 ≤ 6 分 → 立即触发深度复盘
- 用户指出流程问题 → 记录为下次改进项
- 用户修改需求 → 对比原始任务地图，分析需求漂移原因

**经验闭环**（将改进沉淀为持久知识）：

任务结束后，从复盘纪要和用户反馈中提取值得固化的经验，按以下规则处理：

| 改进类型 | 处理方式 | 权限 |
|---|---|---|
| 单次任务教训（如"这类任务不适合并行"） | 追加到 memory 文件，带日期和任务标签 | 自批，只追加不覆盖 |
| 角色配置经验（如"工程任务加测试员效果好"） | 追加到 memory 文件 | 自批，只追加不覆盖 |
| 框架层面改进（如"需要新增一个步骤"） | 告知用户，等确认后修改 skill 主文件 | 需用户确认 |
| 发现反模式或原则需要调整 | 告知用户，等确认后修改 | 需用户确认 |

**可追溯规则**：
- memory 文件只追加，不覆盖已有内容。每次追加带时间戳和来源标注
- 如果要修改已有内容，用分隔线隔开，保留旧版本，标注"已更新于 [日期]"
- skill 主文件的每次修改保存变更摘要（改了什么、为什么改）到 memory
- 这样任何时候都能回溯：什么时候改了什么、为什么改

## 三、角色设计

### 原则：动态生成，模板只是参考

根据任务特征现场生成角色。建议从 3 个开始，按需增减。**角色名称要让用户一眼看懂这个 Agent 干什么**——不要用抽象模板名，用任务语境里的自然称呼。

### 常用模板

| 模板 | 核心职责 |
|---|---|
| 执行者 | 负责具体产出 |
| 批评家 | 对抗性审查，按致命/严重/轻微分级。**含策略批评模式**（见下方） |
| 验收者 | 从原始需求出发评估，防目标漂移。**必须代入服务对象视角**：写文案想读者能不能看懂，写程序想使用者会不会用错，写理论想目标学生跟不跟得上——不是"需求满不满足"，是"用这个东西的人能不能受益" |
| 研究员 | 补充外部知识/数据/案例 |
| 理论家 | 概念定义、逻辑链构建 |
| 架构师 | 设计方案、技术选型 |
| 代码审查员 | 安全性、可维护性 |
| 测试员 | 跑测试、构造边界用例 |
| 整合员 | 合并多执行者的冲突观点 |
| 记录员 | 记录因果链（超 2 轮迭代时引入） |

### 动态生成格式

当模板覆盖不了时，现场生成：

```
角色名：[简洁名称]
视角：[从什么角度看问题]
输入：[需要什么信息]
输出：[应该交付什么]
禁止：[不应该做什么]
```

### 快速参考：任务类型→角色配置

**批评家职责扩展：策略批评模式**

批评家的标准模式是检查"产出是否正确"（逻辑错误、安全隐患、遗漏项）。当出现以下信号时，必须额外激活**策略批评模式**——质疑"解决问题的方法本身是否正确"：

- 同一问题被指出 >= 2 次
- 修复后的版本和上一版改动很小（微调型修改）
- 执行者说"我再试一次"或"换个角度修"

**关键约束：策略批评家必须独立上下文** — 不读执行者当前代码，只读：(a)原始问题描述 (b)修复历史（记录员的因果链） (c)当前症状。防止被执行者的思路带偏。

策略批评输出格式：
- **当前策略**：[一句话描述我们在用什么方法解决]
- **策略质疑**：[这个方法本身有没有问题？是不是在错误的层面修？]
- **替代建议**：[有没有完全不同的解决路径？]

| 类型 | 典型角色组合 |
|---|---|
| 理论探讨 | 理论家 + 研究员 + 批评家 + 验收者 |
| 工程实现 | 架构师 + 执行者 + 代码审查员 + 测试员 |
| 写作创作 | 执行者 + 批评家 + 验收者 |
| 分析研究 | 研究员(并行搜不同方向) + 整合员 + 批评家 |

这些是起点不是终点，根据实际任务调整。

### 选角 3 问

1. 需要哪几个独立视角？（每个视角 = 一个角色）
2. 哪些视角有对抗关系？（必须拆成不同角色）
3. 哪些视角可以合并？（减少 Agent 数量）

## 四、核心原则

1. **先拆解再执行** — 先出任务地图，再派 Agent
2. **强制对抗** — 执行者和批评家不同 Agent，批评家必须存在
3. **需求锚定** — 每轮复述原始需求，逐项评估
4. **版本冻结** — 中等以上任务：产出编号 v1.0→v1.1→v2.0，禁止覆盖。简单任务：用"初版/修订版"即可，不必形式化编号
5. **因果链记录** — 格式：`哪个批评 → 触发了什么改动 → 导致了什么下游变化`
6. **全局审视** — 出现停滞信号时停下来判断：继续攻坚还是换方向？不要在天花板上浪费时间，也不要遇到困难就轻易跳（详见二-第4步）
7. **先评估再自研** — 涉及以下成熟领域时，默认使用已有成熟方案。自研必须满足：(a)已证明现有方案在关键需求上不可行 (b)自研成本已被估算 (c)维护负担已被纳入评估。"我能写出来"不是自研的充分理由
8. **发现即写入** — 任务中产生的任何决策、改进、教训，必须在汇报前写入对应持久文件（skill主文件/memory/项目文件）。禁止"在对话里分析完就算做了"。流程：发现 → 判断归属（skill规则/memory经验/项目记录） → 写入 → 汇报。不是"等用户问才写"，是"不写完不让汇报"。**框架模式下**严格执行；**极简模式下**如发现值得固化的教训，简要记录到 memory 后交付（不写复盘纪要，不走完整流程）

   成熟领域清单（参考示例，不是穷举——进入不熟悉领域时先搜索再决定）：
   - 物理引擎：Planck.js、Matter.js、Box2D
   - 图形渲染：Three.js、PixiJS、Phaser
   - 音频处理：Howler.js、Tone.js
   - 网络通信：Socket.io、WebSocket API
   - 数据存储：IndexedDB、SQLite
   - 加密：Web Crypto API、libsodium
   - HTTP客户端：axios、fetch wrapper

   自研证明模板：
   ```
   现有方案：[库名]
   不可行原因：[具体说明，如"不支持X功能"/"性能不满足Y约束"]
   自研成本估算：[开发时间 + 维护负担]
   决策：自研 / 适配现有库 / 混合方案
   ```
9. **Agent 产出必须验证** — Agent 声称"已修改文件"不可信，可能幻觉、遗漏或改错。Agent 返回具体修改内容和理由，主 AI 自己执行修改（Edit/Write），修改后 Read 验证客观证据。踩坑案例：Sound Designer agent 声称修改了 6 个音效函数，文件中实际未变。

### 实战经验（可迁移的教训）

以下是从实际任务中提炼的跨任务通用经验，直接嵌入框架，不依赖外部记忆：

**关于分工：**
- 假分工是最危险的反模式——不同 Agent 给出几乎相同结论 = 视角没有独立。检验方法：Agent 之间有没有分歧？
- 并行是基本能力，不要自我设限说"只能串行"。能并行的先并行，有依赖的再串行
- 批评家保证质量，验收者保证方向，两者不能互相替代
- 并行前必须检查隐性依赖——"这个 Agent 的产出会不会影响另一个 Agent 的输入？"会的话必须串行

**关于节奏：**
- 做减法比加法重要——框架膨胀到自相矛盾时，精简比继续加更有效
- 不要在天花板上调参数——方案接近最优了还在微调，不如停止交付，把时间花在下一个任务上
- 先读现场再拆解——不读上下文就派 Agent，等于在信息不足时做决策
- 天花板判断：每轮发现新问题 = 值得继续；每轮修同类问题 = 该停了

**关于进化：**
- 复盘纪要里的改进建议如果不回写到持久存储，下次任务就丢失了
- "上次这么做成功了"不能作为唯一理由——每次任务的约束条件可能不同
- 验收者应该每轮出场锚定需求，不只是最后一轮。中间偏了没人喊停，最后纠正成本更高
- Agent 产出后续要用 → 必须先存文件。对话里的输出下一轮 Agent 看不到
- 每轮换不同评估视角比重复同一视角好——不同 Agent 能发现不同类型的盲区
- 按需引入要有触发信号清单——理论任务产出偏学术→场景测试员，多 Agent 结论矛盾→整合者，超 3 轮无进展→流程审计员
- 信息压缩是调度员的核心能力——Agent 产出可能 3000 字，调度员中转给下一个 Agent 时只转关键信息。不压缩 = 上下文窗口被无关内容填满，下游 Agent 注意力被稀释

**关于质量陷阱：**
- 过度宣称（over-claiming）是最常见的开源风险——pilot study 说成"实验验证"、1 个案例说成"普遍规律"。检验方法：把结论里的形容词去掉，剩下的事实还能支撑结论吗？
- 范围漂移（scope-mismatch）比目标漂移更隐蔽——目标没变，但讨论范围悄悄扩大了。例：原计划"审查 3 个机制"，实际变成了"审查整个框架"。每轮对照任务地图的子任务列表，不在列表里的=范围漂移
- Agent 之间的分歧是信号不是噪音——没有分歧可能意味着视角没独立。但分歧持续 2 轮没解决 = 需要整合员介入，不是继续让两个 Agent 吵

## 五、质量红线（必须暂停）

1. **验收者连续两轮给相同批评** → 暂停，触发流程复盘
2. **批评家找不到问题** → 引入第二批评家交叉验证
3. **Agent 产出偏长时** → 建议附一句话摘要（深度分析类任务不限字数，但要保证调度员能快速理解核心结论）
4. **目标漂移** → 产出方向和原始需求不一致，立即纠正
5. **并行 Agent 之间出现依赖错误** → 暂停，改为串行，下次选角色时检查隐性依赖
6. **连续两轮在同一问题上修补没突破** → 先定位根因（方案本身有缺陷？还是执行不到位？），根因不同处理方式不同
7. **同一问题修复计数器** — 由**非执行者**维护（调度员/记录员/其他角色均可，只要不是正在修bug的那个Agent自己计），每轮修改后记录一行：`[轮次] [文件] [函数] [修改类型:症状/架构]`。"同一问题"定义：同一个函数/区域、用户反馈同一症状、修改类型连续为"症状"。达到3次时，调度员强制暂停（不是Agent自愿停止），启动根因诊断流程：(a)复现问题完整链路 (b)定位最早出错的环节 (c)判断是方案缺陷还是执行缺陷。禁止继续在同一层面打补丁。无专职记录员时由调度员自行维护
8. **用户暂停信号** — 用户消息包含"停止/先诊断/别修了/怎么回事/不应该这样"类关键词时，立即暂停Agent执行并汇报：(a)当前进度 (b)卡在哪 (c)下一步计划。**不替用户判断该不该停**——汇报后等用户决定：说"继续"→该做就做；说"别做了"→真的停并启动全局审视

## 六、反模式（禁止做的事）

1. **跳过 0 秒分流器** — 任何任务必须先过三分法，禁止默认启动框架
2. **简单任务走完整流程** — 极简模式已判出但仍派 Agent、写复盘 = 违规
3. **拿到任务就派 Agent** — 非极简模式也必须先拆解
4. **角色只从固定模板选** — 模板是起点，需要时必须现场生成
5. **只有串行没有并行** — 能并行的一起派
6. **记录员记流水账** — 必须记因果链
7. **批评家只夸不批** — 找不到问题就引入第二批评家
8. **验收者缺席** — 中等以上任务每轮出场
9. **生搬硬套流程** — 有更好的方案就用更好的
10. **假分工** — 不同 Agent 给出几乎相同结论 = 假分工。检验：Agent 之间有没有分歧？
11. **在天花板上调参数** — 方案接近最优了还在微调 → 停止交付
12. **遇到困难就跳方案** — 同一问题连续 2 轮没改善才换方向
13. **经验主义** — "上次这么做成功了"不能作为唯一理由。每次任务必须重新审视约束条件
14. **假设任务同质化** — 每次任务可能有新的约束，不能默认套用上次的分工
15. **读了经验不转化** — 读经验后没有写成"本次必须检查：[具体动作]" = 没读。经验是装饰品不是决策依据
16. **跳过自检或审计（框架模式）** — 框架模式下，调度员元检查+审计员审计必须执行。跳过元检查→本轮未完成；跳过审计（无合理原因）→强制触发。极简模式不需要自检和审计（跳过整个流程）
17. **depends_on 只填执行依赖没填信息依赖** — 导致并行 Agent 看不到影响自己决策的关键信息。逐对检查：A 的产出结论是否影响 B 的设计选择？是→B depends_on A
18. **跳过计划审查直接执行** — 计划的错误在执行后才发现，返工成本 10 倍。调度声明输出前必须经过计划审查 Agent
19. **计划审查 Agent 只说"看起来不错"没有具体检查** — 等于没审查。审查必须逐项对照 5 个检查点给出 pass/fail
