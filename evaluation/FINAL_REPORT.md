## 三、Mini-Validation：独立审查测试

### 方法

取 MiMo 生成的 D4（限流）和 D5（支付）代码，由全新对话进行独立审查：
- 无 Skill：直接给代码，要求"找潜在问题"
- 有 Skill：框架模式（架构师设计审查 + 批评家对抗审查）

### 结果

**D4 限流（代码本身已正确处理竞态）：**

| 预埋 bug | 无 Skill | 有 Skill |
|----------|:------:|:------:|
| B1-竞态条件 | 0 | 0 |
| B2-时钟偏移 | 0 | 0 |
| B3-Retry-After 攻击 | 0 | 0 |
| **小计** | **0/9** | **0/9** |

原因：代码用 Lock + Lua 做到了原子性（B1 已正确实现），时钟偏移和攻击向量不在审查者关注范围内。

**D5 支付幂等（代码有架构级缺陷）：**

| 预埋 bug | 无 Skill | 有 Skill |
|----------|:------:|:------:|
| B1-请求体篡改 | 0 | **3** |
| B2-分布式锁过期 | 0 | 0 |
| B3-状态机缺失 | 0 | **3** |
| **小计** | **0/9** | **6/9** |

批评家命中：
- B1："同一 idempotency_key 不校验请求参数一致性（金额等），可能返回不匹配的缓存结果"
- B3："PROCESSING 僵死锁：payment_fn 卡住或崩溃后，key 永久锁死，无恢复机制"

无 Skill 审查的额外发现（非预埋）：
- f-string 语法错误（致命）——代码无法执行
- 失败重试僵尸记录（严重）——重试路径死循环

### 验证结论

| 维度 | 结论 |
|------|------|
| 有 Skill vs 无 Skill 审查 | D5 上 6/9 vs 0/9，批评家的对抗性视角是关键增量 |
| 批评家擅长的 bug 类型 | 攻击面推演（请求体篡改）、状态机漏洞（僵死锁） |
| 批评家不擅长的 bug 类型 | 分布式基础设施（锁 TTL、时钟偏移）、文件系统语义 |
| 无 Skill 审查的价值 | 擅长代码级 bug（语法错误、逻辑错误），不擅架构级风险 |

## 五、关键发现

### 1. 无 Skill 基线跨模型一致为 0

两个模型在无 Skill 模式下都是 0/54。LLM 在"写代码"模式下忠实执行需求，从不主动质疑设计本身。这不是特定模型的缺陷，而是通用现象。

### 2. MiMo 9 vs DeepSeek 10，基本持平

原始测试 MiMo 34/54 vs DeepSeek 10/54 的巨大差距被证实是双重偏差：
- 同对话污染（无 Skill 基线 0/54 不可信）
- 评分标准不一致（"代码正确" vs "识别了 bug"不可混用）

统一标准后，两者增量接近（+9 vs +10），符合"MiMo 并不比 DeepSeek 强"的直觉判断。

### 3. 批评家的增量集中在特定 bug 类型

| 批评家擅长 | 批评家弱项 |
|-----------|-----------|
| 竞态条件 / 原子性 | 时钟偏移 / 分布式同步 |
| 状态机漏洞 / 僵死状态 | 锁过期 / TTL 管理 |
| 请求体篡改 / 攻击面 | 文件系统语义（符号链接） |
| 计算精度（Retry-After） | 数据完整性（部分提交） |

### 4. 分流器直接影响审查深度

D1 被判极简模式→跳过批评家→0/9。D4/D5 被判框架模式→批评家介入→5/9 和 3/9。分流器的 Q2/Q3 判断决定了是否投入审查资源。

### 5. 批评家额外发现的价值

除预埋 bug 外，批评家在各任务中额外发现了约 30 个（MiMo）/ 15 个（DeepSeek）非预埋的真实问题，含多个致命级（SQL 注入、引用赋值回退失效、锁释放无原子性）。预埋 bug 偏向架构/安全/分布式领域，批评家的强项在代码质量/工程实践——两者存在错位。

## 六、方法论改进

### 已验证的问题

| 问题 | 影响 | 修复 |
|------|------|------|
| 同对话污染 | 基线分数失真 | 每个条件独立对话 |
| 评分标准不一致 | 跨模型不可比 | 统一采用 DeepSeek 标准 |
| 任务类型混淆 | "写代码"和"找 bug"混测 | 拆分为生成/审查/闭环三阶段 |
| 样本量不足 | 18 个 bug 不够区分真实差异 | Mini-Validation 增加数据点 |

### 推荐的完整测试方案

三阶段隔离测试：

1. **阶段 1：代码生成**（基线）—— 每模型 × 无 Skill，全新对话，只给需求
2. **阶段 2：独立审查**（核心）—— 阶段 1 代码 → 全新对话审查，有/无 Skill 各跑
3. **阶段 3：完整闭环**（端到端）—— 有 Skill，写→审→修，评修复质量

每组合 = 全新空白对话，评分表不暴露，交替执行抵消顺序效应。

---

## 七、结论

1. **Multi-Agent Skill 对 LLM 代码审查能力有增量，但幅度有限**（+9~10/54，约 17-19%）
2. **增量来自批评家的对抗性视角**，不是框架流程本身
3. **批评家不是万能的**：擅长代码正确性和攻击面分析，弱于分布式系统和文件系统语义
4. **两个模型的审查能力在同一水平**：MiMo 9/54 vs DeepSeek 10/54
5. **原始测试的 34/54 不可信**：同对话污染 + 评分标准不一致是主因
6. **无 Skill 审查也有独特价值**：擅长找代码级 bug（语法、逻辑），与批评家形成互补
