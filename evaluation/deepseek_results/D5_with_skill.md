## 探针分析

- **表面需求**：幂等键去重
- **深层需求**：防止重复扣款 = 金融级安全保障
- **相关需求**：审计追踪、幂等键安全（防预测/碰撞）、超时处理
- **建议路径**：先设计并发安全协议，再实现存储层

## 任务地图

```
- 任务类型：工程实现
- 经验注入：无
- 子任务：
  - T1: 幂等协议设计 — 架构师，产出：状态机 + 并发处理协议，depends_on: []
  - T2: 存储层实现 — 执行者，产出：Redis + 内存双模式，depends_on: [T1]
  - T3: 幂等键生成 + 安全 — 执行者，产出：key 生成器，depends_on: [T1]
  - T4: 并发测试 — 测试员，产出：竞态测试，depends_on: [T2, T3]
```

## 批评家反馈（关键发现）

1. **致命**：TOCTOU 竞态 — 多个请求同时读（key 不存在）→ 都执行扣款 → 引入 `SET NX` 原子创建
2. **严重**：processing 状态无超时 — 如果执行者崩溃，后续请求永远等待 → 增加 TTL + 超时恢复
3. **建议**：幂等键应防预测 → SHA256 而非自增 ID

## 最终产出

`D5_payment_idempotent/payment_idempotent.py` — 三层并发安全（快速路径/等待路径/竞态路径）
