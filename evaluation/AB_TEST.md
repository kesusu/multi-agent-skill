# A/B 测试设计与记录

> **数据质量声明**：第二轮实验（MiMo D1-D6，34/54）的数据已被排除。
> 原因：同对话污染 + 评分标准不一致。详见 `FINAL_REPORT.md`。
> 有效数据：MiMo 重评 9/54（SCORING_SHEET.md）、DeepSeek 10/54（deepseek_results/SUMMARY.md）。

## 实验设计

**实验组**：使用 multi-agent skill（`/multi-agent <任务>`）
**对照组**：不用 skill，直接给 Claude Code 同样的任务描述
**评估方式**：功能差检验（不做假盲评，直接对比"好在哪、差在哪"）

> 不假装不知道哪边用了 Skill——Skill 产出有明确结构化特征，任何 LLM 一眼能识别。
> 不问"哪个更好"（打分容易模糊），问"好在哪、差在哪、你愿意为哪个多付钱"。

---

## 3 个任务（覆盖极简→复杂梯度）

| 任务 | 类型 | 测试什么 |
|---|---|---|
| A | 极简：事实性问题 | 前置分流器是否正确触发极简模式，不浪费资源 |
| B | 中等：代码解释 | 结构化输出是否带来实际增量价值 |
| C | 复杂：方案设计 | 多 Agent 并行分工的深度优势 |

### 任务 A（极简）
> "Python 的 `*args` 和 `**kwargs` 有什么区别？"

预期：分流器判极简模式，直接回答，不派 Agent、不写复盘。如果 skill 版反而更慢更啰嗦 = 分流器失败。

### 任务 B（中等）
> "解释这段代码的作用，并指出潜在问题：
> ```python
> def process(data):
>     result = []
>     for i in range(len(data)):
>         if data[i] > 0:
>             result.append(data[i] * 2)
>     return result
> ```"

预期：skill 版启动批评家/代码审查员，分级别输出问题。关键比较：是否找到了对照组没找到的问题？

### 任务 C（复杂）
> "设计一个多人协作文档的冲突解决方案。约束：10人同时编辑、离线5-30分钟、版本历史+回滚、自动合并。"

预期 Skill 触发：
- 前置分流器 → 框架模式（要方案、跨领域、有约束）
- 多 Agent 并行 → 架构师（数据模型+合并策略）+ 存储工程师（持久化方案）+ 场景压力测试员（极端场景推演）
- 批评家 → 找因果序可靠性、客户端缓存策略等设计漏洞
- 验收者 → 对照 4 个约束条件逐项检查

关键：需求明确，两边解同一道题，差异只来自"解题方法"（单 Agent vs 多 Agent 协作）。

---

## 评估问题（每个任务必答）

**问题 1**：Skill 组做了什么，对照组没做？（定位增量价值）
**问题 2**：对照组做了什么，Skill 组没做？（定位代价或遗漏）
**问题 3**：如果这个任务是付费的，你愿意为哪个多付 10 块钱？为什么？（强制价值判断）
**问题 4**（任务 C 追加）：对照组的方案有没有漏洞，是 Skill 组的批评家/验收者能发现但对照组自己没发现的？（直接测对抗审查价值）

## AI 评估者双版本验证（预实验阶段）

两个版本分别跑，结论一致才可靠。

### 版本 A（中立）
> 你是一位中立的任务质量分析师。以下两份产出是同一任务的不同执行方式。
> 请直接回答 3 个问题：
> 1. 产出 A 做了什么，产出 B 没做？
> 2. 产出 B 做了什么，产出 A 没做？
> 3. 如果这个任务是付费的，你愿意为哪份多付 10 块钱？为什么？

### 版本 B（反 Skill）
> 你是一位偏好简洁直接、认为结构化框架通常浪费时间的分析师。
> 以下两份产出是同一任务的不同执行方式，其中一份使用了多 Agent 协作框架。
> 请直接回答 3 个问题：
> 1. 有框架的那份做了什么，另一份没做？
> 2. 没框架的那份做了什么，有框架的那份没做？
> 3. 如果这个任务是付费的，你愿意为哪份多付 10 块钱？为什么？

**可靠性判断**：
- 两个版本结论一致 → 结论可靠，可进入真人验证
- 两个版本结论矛盾 → 受评估者偏好驱动，必须真人验证

### 任务 C（复杂）：多人协作文档冲突解决方案设计

**任务描述**：为多人协作文档编辑系统设计冲突解决方案（10 人、离线 5-30 分钟、版本历史+回滚、自动合并）

**对照组产出摘要**：直接给出完整方案，含数据模型（Document→Branch→Version→Operation）、冲突检测、OT+CRDT 三层合并、3 层存储、6 个潜在问题。1 轮交付。

**实验组产出摘要**：分流器判框架模式，4 角色（架构师/存储工程师/场景压力测试员/批评家）分 2 批并行调度。批评家找到 2 个严重问题（Lamport 时钟因果链断裂、客户端缓存缺失）并修正。2 轮交付 v2.0。

#### 自己评估（调度员视角）

| 问题 | 回答 |
|---|---|
| 1. Skill 组做了什么，对照组没做？ | 批评家找到 2 个严重问题（HLC 因果链断裂+客户端缓存缺失）；场景测试员做了极端场景的具体计算量推演；加了敏感操作审计层 |
| 2. 对照组做了什么，Skill 组没做？ | 数据模型有 Branch 概念（网络分区下的分支建模）；更简洁无框架开销；同样覆盖全部 4 个约束 |
| 3. 付费意愿？ | 多付 10 块给 Skill 组。批评家找到的 2 个问题是真实设计漏洞，上线后修复成本远高于 10 块 |
| 4. 对照组决策有没有经过对抗检验？ | 对照组给了理由但没人挑战（Lamport 时钟没被质疑）。Skill 组：架构师选 Lamport → 批评家挑战 → 改 HLC。真正的对抗性修正 |

## 汇总（3 个任务已跑）

| 任务 | 复杂度 | Skill 增量价值 | Skill 代价/遗漏 | 付费意愿 | 可靠性 |
|---|---|---|---|---|---|
| A（极简） | 最低 | 分流器正确判极简模式，跳过全部流程 | 信息增量极小 | 不多付 | 自评 |
| B（中等） | 中 | 分流器正确判极简模式 + 多发现 1 个边界问题 | 多了分流器开销（极小） | 不多付 | 自评 |
| C（复杂） | 高 | 批评家找到 2 个严重问题 + 极端场景量化推演 + 对抗性修正设计决策 | 没建模 Branch 概念；框架开销更大 | 多付 10 块 | 自评 |

**核心发现**：
1. 分流器全场景正确：从最简（A）到中等（B）都判极简模式不浪费资源，复杂（C）才启动框架模式
2. Skill 的价值不在"产出更多"，在"找到对照组漏掉的问题"——批评家是 MVP
3. 对照组方案不差但不会质疑自己的设计选择——多 Agent 的对抗审查弥补了这个盲区
4. 代价：多 Agent 不保证覆盖度更高，保证的是审查更严

## 第二轮实验：MiMo 深度评估（D1-D6，预埋 Bug 法）

### 实验信息
- 模型：MiMo
- 任务数：6（3 中等 + 3 复杂），每任务预埋 3 个 bug
- 时间：2026-05-31
- 评估方式：预埋 bug 发现率（满分 9/任务，总计 54 分）
- 详细数据：`mimo_results/` 目录

### 结果汇总

| 任务 | 难度 | 领域 | 无 Skill | 有 Skill | 增量 |
|---|---|---|---|---|---|
| D1 文件去重 | 中等 | CLI 工具 | 0/9 | 3/9 | +3 |
| D2 分页封装 | 中等 | REST API | 0/9 | 5/9 | +5 |
| D3 配置热更新 | 中等 | 文件监控 | 0/9 | 4/9 | +4 |
| D4 限流中间件 | 复杂 | 分布式系统 | 0/9 | 6/9 | +6 |
| D5 支付幂等性 | 复杂 | 支付安全 | 0/9 | 7/9 | +7 |
| D6 ETL 管道 | 复杂 | 数据工程 | 0/9 | 9/9 | +9 |
| **合计** | | | **0/54** | **34/54** | **+34** |

### 核心发现
1. 无 Skill 组全部 0/54——模型不质疑自己的设计，忠实执行需求
2. 有 Skill 组 34/54（63%），批评家是唯一增量来源
3. 批评家发现率与领域熟悉度正相关：ETL(9/9) > 支付(7/9) > 分布式(6/9) > 配置(4/9) > REST(5/9) > 文件工具(3/9)
4. 批评家擅长代码结构+分布式+安全问题，弱于文件系统语义和攻击向量推演
5. 批评家额外发现约 30 个非预埋的真实问题（含 4 个致命级）

**方法论偏差**：本次实验在同一个对话中执行无 Skill 和有 Skill 两组，存在上下文污染。无 Skill 组 0/54 可能被低估（真实基线约 1-3/任务）。数据定性结论可靠（批评家能发现哪些类型的问题），定量分数不可直接引用。DeepSeek 实验将采用全新空白对话隔离执行。

详见 `mimo_results/SUMMARY.md`「方法论偏差声明」。

## 第三轮实验：DeepSeek 深度评估（D1-D6，预埋 Bug 法）

### 实验信息
- 模型：DeepSeek-v4-pro
- 任务数：6（同 MiMo 的 D1-D6）
- 时间：2026-05-31
- 方法：12 个全新空白对话，交替抵消顺序效应
- 详细数据：`deepseek_results/` 目录

### 结果汇总

| 任务 | 难度 | 领域 | 无 Skill | 有 Skill | 增量 |
|---|---|---|---|---|---|
| D1 文件去重 | 中等 | CLI 工具 | 0/9 | 0/9 | +0 |
| D2 分页封装 | 中等 | REST API | 0/9 | 3/9 | +3 |
| D3 配置热更新 | 中等 | 文件监控 | 0/9 | 1/9 | +1 |
| D4 限流中间件 | 复杂 | 分布式系统 | 0/9 | 1/9 | +1 |
| D5 支付幂等性 | 复杂 | 支付安全 | 0/9 | 4/9 | +4 |
| D6 ETL 管道 | 复杂 | 数据工程 | 0/9 | 1/9 | +1 |
| **合计** | | | **0/54** | **10/54** | **+10** |

### 跨模型对比

| | MiMo (Claude) | DeepSeek |
|---|---|---|
| 无 Skill 总分 | 0/54 | 0/54 |
| 有 Skill 总分 | 34/54 | 10/54 |
| 预埋 bug 发现率 | 63% | 18.5% |
| 致命级额外发现 | 4 个 | 1 个 |
| 最强领域 | ETL（9/9） | 支付（4/9） |
| 批评家额外发现 | ~30 个 | ~15 个 |

### 核心发现

1. **无 Skill 基线跨模型一致**：两个模型无 Skill 组均为 0/54，验证了"LLM 默认不质疑设计"是跨模型的稳定现象
2. **Skill 增量有跨模型差异**：DeepSeek +10 vs MiMo +34，差距来自批评家的审查深度。DeepSeek 批评家倾向"建议"级别反馈，MiMo 批评家产出"致命/严重"级别
3. **Q3 代价门禁是关键变量**：D5 支付是唯一触发"代价大"判定的任务，也是 DeepSeek 最高分(4/9)。其余 5 个任务被判"代价不大"→批评家走快速通道→遗漏深层架构问题
4. **批评家的注意力分布与预埋 bug 错位**：DeepSeek 批评家擅长代码质量/工程实践（文件分块、错误隔离），但我们的预埋 bug 偏向架构/安全/分布式。批评家发现了 ~15 个真 bug，但只有 2.5 个在预埋列表里
5. **已验证 MiMo 方法论偏差**：MiMo 实验在同一对话中执行两组存在上下文污染，本次 12 个全新空白对话的结果更可靠

### 方法论改进

- 12 个全新空白对话，零上下文污染
- 交替执行抵消顺序效应（D1无→D2有→D3无→...→D1有→...→D6无）
- 每个任务独立目录，含测试数据（D1 有重复文件、D3 有 config.json、D6 有 CSV+schema）
- 有 Skill 组严格先 `/multi-agent` 再粘贴任务描述

详见 `deepseek_results/SUMMARY.md`。
